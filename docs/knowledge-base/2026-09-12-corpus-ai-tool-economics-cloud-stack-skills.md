## 1. Paid vs free is an economic signal, not a capability equivalence

The first and repeated free/paid comparisons demonstrate a useful discovery pattern: users evaluate stacks by recurring cost and substitute lower-cost tools where requirements permit.

The architecture should therefore model:

- subscription price;
- usage-based price;
- free-tier quota;
- seat/user pricing;
- feature-gated tiers;
- API versus UI access;
- storage/compute cost;
- switching cost;
- migration effort;
- licensing constraints;
- data/privacy constraints.

A free provider must never be assumed equivalent to a paid provider. `FREE ≠ UNRESTRICTED` and `CHEAPER ≠ EQUIVALENT`.

## 2. Economic-aware routing

Provider selection should support an explicit optimization objective instead of a static “best tools” list.

```text
TASK CONTRACT
  ├─ capability floor
  ├─ quality floor
  ├─ modality
  ├─ privacy class
  ├─ latency budget
  ├─ monetary budget
  └─ provenance requirement
          ↓
CANDIDATE SET
          ↓
CONSTRAINT FILTER
          ↓
COST / QUALITY OPTIMIZATION
          ↓
AUTHORIZED ROUTE
```

When a fallback changes quality, privacy, modality, context limits or licensing, the substitution must be surfaced rather than silently applied.

## 8. Verification boundaries

The graphics contain numerous claims that can become stale or ambiguous:

- free versus paid status;
- price;
- model/version names;
- feature availability;
- ranking such as “best” or “most powerful”;
- income claims;
- service existence;
- integration availability.

Therefore:

`GRAPHIC ≠ CURRENT PRODUCT REGISTRY`

`LIST RANKING ≠ BENCHMARK EVIDENCE`

`PRICE CLAIM ≠ CURRENT PRICE`

`SKILL LIST ≠ LABOR-MARKET PROOF`

`CLOUD SERVICE MAP ≠ DEPLOYMENT VALIDATION`
