## 5. Current architectural strength

The strongest existing common pattern is a separation between:

`intent → evidence/context → reasoning → policy/authorization → capability → deterministic execution → authoritative readback → verification → audit → measured outcome`

The portfolio already encodes important invariants including separation of model capability from authorization, typed capabilities, explicit human approval states, durable task state, provenance-aware evidence, bounded multimodal context, deterministic side-effect execution and postcondition verification.

## 6. Primary governance gap discovered

The portfolio has evolved faster than its canonical registry. The repository contains later projects that are not all represented consistently in the canonical project index. The immediate consequence is avoidable ambiguity when determining:

- canonical project identity;
- lineage and supersession;
- project maturity;
- dependency relationships;
- which project owns a capability;
- whether a newly proposed project duplicates an existing convergence layer.

This is a governance/integrity problem, not merely documentation polish.

## 7. Engineering maturity gap

The repository is unusually strong at architecture specifications, research synthesis and design invariants. The next bottleneck is operationalization: converting the portfolio from a large collection of architecture-ready specifications into reproducible implementation, verification and release pipelines.

A recurring opportunity is to add executable contracts around project manifests, tests, security checks, observability and evidence rather than continuing to add specification-only projects.

## 11. Rule for incoming knowledge

New files, links and research supplied after this baseline must be processed as new evidence. They should be mapped to:

`knowledge → existing project impact → implementation opportunity → new project candidate → verification requirement`

No new project should be created solely because a new source document uses novel terminology. Duplication, maintenance burden, security impact and measurable value must be evaluated first.
